# How VkVita works

This is a map of the code for people who want to change it or find a bug.
How to use VkVita is in the README. What is supported is in COVERAGE.md.

## The big picture

Vulkan and GXM are close to each other in many places. Both have command
buffers, render targets, programs with uniform buffers and explicit sync.
The biggest difference is when work happens:

- In Vulkan you record a command buffer once and submit it later, maybe
  many times.
- GXM has one context, and you call it directly while a scene is open.

So VkVita records every `vkCmd*` call into a plain byte array. At
`vkQueueSubmit` it walks that array and makes the real GXM calls. Almost all
the interesting work happens in that replay.

```
app ──vkCmd*──▶ vkv_cmd.c ──bytes──▶ command buffer
                                        │
app ──vkQueueSubmit────────────────────▶ vkv_queue.c  (replay loop)
                                        ├─ vkv_draw.c      draws
                                        ├─ vkv_clear.c     clears
                                        ├─ vkv_transfer.c  copies, blits
                                        └─ GXM scenes ──▶ GPU
app ──vkQueuePresentKHR──▶ vkv_swapchain.c ──▶ display queue
```

A render pass becomes one GXM scene, or more if it has several subpasses
or needs a split. `sceGxmBeginScene` runs at `vkCmdBeginRenderPass` during
replay and `sceGxmEndScene` runs at the end.

## Objects

Every Vulkan handle is a pointer to a VkVita struct (`VkImage` points to a
`VkvImage`, and so on). Each struct starts with a `VkvObject` that holds a
magic number. With validation on, `VKV_OBJ_OK` checks it, so a destroyed or
wrong handle is reported instead of crashing.

## Memory

The Vita has two kinds of GPU visible memory: CDRAM (the video memory) and
uncached main RAM. Memory type 0 is CDRAM and type 1 is RAM. Large
allocations get their own kernel memory block. Small ones (up to 512 KiB)
come out of shared blocks through a first fit sub-allocator
(`vkv_memory.c`). Both memory types are host visible and coherent, so
mapping is just a pointer.

Images are laid out the way GXM expects them (`vkv_image_setup_layout`).
Linear images have rows aligned to 8 texels. Cube maps and compressed
textures are swizzled. Render targets are aligned to 4 KiB.

## Shaders

A shader module can be one of three things:

1. A GXP binary, used as it is.
2. Cg source, compiled with vitaShaRK at pipeline creation.
3. SPIR-V. `vkv_spirv_lower.c` first rewrites the parts GXM cannot do. Then
   SPIRV-Cross turns it into HLSL and `vkv_spirv.c` rewrites that into the
   Cg dialect of the Sony compiler. After that it goes the same way as Cg.

Compiled programs can be cached as `.gxp` files by hash, so later starts
skip the compiler. `SHADERS.md` has the details of the translation.

## Pipelines and uniforms

A pipeline holds registered GXM programs from the shader patcher and all the
fixed state: blend, depth, stencil, cull, topology. GXM gets uniforms from
default uniform buffers that are reserved per draw. At pipeline creation,
VkVita builds a uniform map (`VkvUniformMap`). For each GXM program
parameter it records where the value comes from: a push constant range or
a descriptor binding with an offset. `vkv_write_uniforms` in `vkv_draw.c`
copies those values in at every draw. That way uniform buffers can be
rewritten every frame without any sync.

## Sync

Each scene writes a serial number into a GXM notification when the GPU is
done with it. Fences, queries and the "is this image still in use" checks
compare against that number (`vkv_serial_done`). `vkv_device_wait_gpu` waits
for everything. CPU side copies call it when the GPU could still be using
the memory.

The transfer unit (fills and image copies) runs next to the scenes.
Transfers wait for the sync object of the image they write, and the next
scene waits for earlier transfers (`SCE_GXM_SCENE_FRAGMENT_TRANSFER_SYNC`).

## Things GXM does differently

These shaped a lot of the code:

- No viewport clipping. The region clip is set to viewport and scissor
  combined, on 32x32 tiles. A scissor that is not tile aligned uses a
  fragment program variant that discards the rest.
- No line strips. They are drawn as line lists of vertex pairs.
- No framebuffer fetch. Input attachments become textures read at the
  current pixel.
- A scene without draws does not store its depth buffer, so a depth clear in
  such a scene is carried over to the next one.
- MSAA color is resolved when tiles are written, so multisampled color
  images only hold the averaged pixels.
- The softfp VitaSDK passes floats the wrong way to some GXM functions.
  `vkv_internal.h` redirects those with `pcs("aapcs-vfp")`.

## Testing without a Vita

`tests/host/run_host_tests.sh` builds VkVita and all samples for Linux
against `tests/host/mock_sce.c`. The mock implements the GXM, display, ctrl
and memory functions closely enough to run every sample with AddressSanitizer
and to check things like matching multisample modes. Crashes and validation
errors show up there before anything goes onto real hardware.

`samples/shader_tests` is the hardware check: every tile tests one feature
on the GPU and turns green when it works.
